Experiment from 2026-10-18, first program for the STM32 NUCLEO-L552ZE-Q board.

Cycles the three user LEDs (red PA9, green PC7, blue PB7) and prints
`red`, `green`, `blue` to the console. The LEDs are already defined in
the board DTS, so no overlay is needed.

## Setup (Linux)

1. Install `openocd` from the distro. It ships udev rules for ST-LINK
   (`/usr/lib/udev/rules.d/60-openocd.rules`). Replug the board afterwards,
   the rules apply only to newly connected devices.
2. Be in the `dialout` group for the console on `/dev/ttyACM0` (115200 8N1).

The board's default runner is STM32CubeProgrammer, which I don't have
installed, so flash with `-r openocd`.

## Build and flash

```
west build -p -b nucleo_l552ze_q .
west flash -r openocd
```

Use the plain `nucleo_l552ze_q` target. The `nucleo_l552ze_q/stm32l552xx/ns`
variant is for TF-M and changes the TrustZone option bytes.

## Notes

- The on-board ST-LINK/V2-1 (an STM32F103) is a USB composite device: SWD
  debug (libusb, no kernel driver), mass storage (drag-and-drop `.bin`), and
  a CDC ACM virtual serial port. See `lsusb -v -d 0483:374b`.
- The ST-LINK serial port buffers output while the port is closed, so the
  first lines after opening it may come from the old firmware.
- PA9 (red LED) is also USART1 TX, and PB7 (blue LED) is also I2C1 SDA.

## Side note: running `samples/basic/blinky_pwm`

The sample doesn't build for this board out of the box.
`blinky_pwm/nucleo_l552ze_q.overlay` fixes that, with no change to `main.c`:

```
cd ~/zephyrproject/zephyr
west build -p -b nucleo_l552ze_q samples/basic/blinky_pwm -- \
    -DEXTRA_DTC_OVERLAY_FILE=<path-to>/blinky_pwm/nucleo_l552ze_q.overlay
west flash -r openocd
```

Why the overlay is needed:

1. **No `pwm-led0` alias.** The sample looks up `DT_ALIAS(pwm_led0)`. The
   board DTS only describes the LEDs as plain GPIOs, so the build fails with
   `__device_dts_ord_DT_N_ALIAS_pwm_led0_... undeclared`.

2. **Hardware PWM comes from a timer, not from the GPIO.** On STM32, PWM is
   generated by the general-purpose timers (TIMx). Each timer has a counter
   and up to 4 channels, and each channel can drive certain pins. A pin is
   connected to a peripheral by setting its *alternate function* (AF) in
   the GPIO registers. The datasheet's "alternate function mapping" table
   shows which pin can be what. In Zephyr this is the `pinctrl` property,
   and the HAL already provides named nodes such as `tim4_ch2_pb7` in
   `modules/hal/stm32/dts/st/l5/stm32l552z(c-e)txq-pinctrl.dtsi`.
   The LED pins can be routed to these timers:

   | LED  | Pin | Timer channels       |
   |------|-----|----------------------|
   | red  | PA9 | TIM1_CH2             |
   | green| PC7 | TIM3_CH2, TIM8_CH2   |
   | blue | PB7 | TIM4_CH2, TIM17_CH1N |

   So the overlay enables `timers4` and its `pwm` child node, routes PB7 to
   channel 2, and defines a `pwm-leds` node with the `pwm-led0` alias.

3. **A 16-bit timer needs a prescaler.** The timer counts at its input clock
   divided by `prescaler + 1`. One PWM period is one run of the counter
   from 0 up to the auto-reload value (ARR). Here the timer clock is 110 MHz
   (the APB1 prescaler is 1), and TIM4's counter and ARR are 16-bit. With the
   default `st,prescaler = <0>`, the longest period is
   65536 / 110 MHz ≈ 0.6 ms. The sample wants up to 1 s, so it fails at
   runtime with `period cycles 110000000 exceeds 16-bit timer limit`.
   `st,prescaler = <10999>` gives a 10 kHz tick: periods up to 6.5 s, in
   100 µs steps. The cost is coarse duty-cycle resolution at short periods.
   For audio or motor PWM you'd use a small prescaler and a short period.
   TIM2 and TIM5 are 32-bit and wouldn't need this, but they don't reach
   the LED pins.
